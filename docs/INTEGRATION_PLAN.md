# План інтеграції BAS Роздрібна торгівля для України з LOYAL CARDS API

## Принцип: BAS — керуюча система

**Усі нарахування, списання, активації та згоряння бонусів обліковуються виключно в BAS** через рухи регістрів, прив'язані до документів-реєстраторів. LOYAL CARDS API — зовнішній канал відображення: після формування рухів BAS **асинхронно** передає поточний доступний баланс (`balance`) та рівень (`discount`) на wallet-картку.

```
ЧекККМ / Повернення / Регламент
         │
         ▼
  Формування рухів по регістрах  ◄── джерело істини
         │
         ▼
  LC_СинхронизацияLoyalCards   ◄── лише відображення
         │
         ▼
     loyal.ws API (balance)
```

---

## 1. Аналіз API (loyal.ws, v1.0.3)

LOYAL CARDS керує wallet-картками (Apple/Google Wallet). API **не** реалізує:
- затримку активації 14 днів;
- термін дії 4 місяці;
- FIFO-списання;
- облік повернень.

Це все — в BAS. API використовується для:
- ідентифікації картки (`tel`, `memberId`, `serialNumber`);
- створення картки;
- оновлення `balance` / `discount` після рухів у BAS.

| Метод | Шлях | Коли викликати |
|-------|------|----------------|
| POST | `/api/auth/login` | Перед будь-яким запитом (кеш токена) |
| GET | `.../values?tel=` / `?memberId=` | Ідентифікація на касі |
| POST | `.../pass/memberId` | Випуск нової картки |
| PUT | `.../values/balance` | **Після** рухів по регістрах |
| PUT | `.../values/discount` | При зміні рівня лояльності |

## 2. Об'єкти метаданих

### 2.1. Регістр накопичення `LC_БонусныеБаллыКлиентов` ⭐

**Тип:** залишки (Balance).  
**Реєстратори:** `ЧекККМ`, `ВозвратТоваровОтПокупателя`, `LC_КорректировкаБонусов` (службовий), регламентне завдання через `LC_ОперацияБонусов` (службовий документ).

| Вимір | Тип | Опис |
|-------|-----|------|
| `Контрагент` | СправочникСсылка.Контрагенты | Власник бонусів |
| `ПартияБонусов` | СправочникСсылка.LC_ПартииБонусов | Партія для FIFO |
| `СостояниеБонусов` | Перерахування.LC_СостоянияБонусов | `ОжидаетАктивации` / `Доступны` |

| Ресурс | Тип | Опис |
|--------|-----|------|
| `Количество` | Число(15,2) | Кількість бонусів (1 бонус = 1 грн) |

**Логіка рухів:**

| Подія | Вид руху | Состояние | Опис |
|-------|----------|-----------|------|
| Проведення чека (нарахування) | Приход | `ОжидаетАктивации` | 5% від грошової частини |
| Регламент (активація) | Расход | `ОжидаетАктивации` | Списання з «очікування» |
| Регламент (активація) | Приход | `Доступны` | Зарахування в доступні |
| Списання на касі | Расход | `Доступны` | FIFO по партіях |
| Регламент (згоряння) | Расход | `Доступны` | Невикористаний залишок |
| Повернення товару | Расход/Приход | за сценарієм | Скасування нарахування / повернення списаних |
| Скасування проведення чека | Сторно | — | Зворотні рухи |

**Запити балансу на касі:**
- Доступно = залишок за `СостояниеБонусов = Доступны`
- Очікує активації = залишок за `СостояниеБонусов = ОжидаетАктивации`
- Всього = сума обох

---

### 2.2. Регістр відомостей `LC_ПартииБонусов` ⭐

**Тип:** неперіодичний, підчинений документу.  
**Реєстратор:** `ЧекККМ`, `ВозвратТоваровОтПокупателя`, `LC_ОперацияБонусов`.

| Вимір | Тип |
|-------|-----|
| `ПартияБонусов` | СправочникСсылка.LC_ПартииБонусов |

| Реквізит | Тип | Опис |
|----------|-----|------|
| `Контрагент` | Контрагенты | |
| `ДокументОснование` | ДокументСсылка | Чек / повернення |
| `ДатаНачисления` | Дата | Дата покупки |
| `ДатаАктивации` | Дата | +14 календарних днів |
| `ДатаСгорания` | Дата | +4 міс. від активації |
| `СуммаНачислена` | Число(15,2) | Початкова сума |
| `УровеньЛояльности` | LC_УровниЛояльности | Правила на момент нарахування |
| `Активирована` | Булево | Прапорець (для швидкого відбору) |
| `Сгорела` | Булево | |

---

### 2.3. Регістр накопичення `LC_БонусныеБаллыОборот` (оборотний)

**Тип:** обороти (Turnover).  
**Призначення:** повна історія рухів для звітів і аудиту.

| Вимір | Тип |
|-------|-----|
| `Контрагент` | Контрагенты |
| `ВидОперации` | LC_ВидыБонусныхОпераций |

| Ресурс | Тип |
|--------|-----|
| `Количество` | Число(15,2) |

Рухи формуються **паралельно** з `LC_БонусныеБаллыКлиентов` у тому ж обробнику проведення.

---

### 2.4. Регістр відомостей `LC_ОчередьСинхронизацииLoyalCards`

**Призначення:** черга відкладеної синхронізації балансу з API (офлайн-каси, помилки мережі).

| Вимір | Тип |
|-------|-----|
| `Контрагент` | Контрагенты |

| Реквизити | Тип |
|-----------|-----|
| `ДатаИзменения` | Дата |
| `ДоступныйБаланс` | Число(15,2) |
| `Синхронизировано` | Булево |
| `ДатаСинхронизации` | Дата |
| `ТекстОшибки` | Рядок(500) |

---

### 2.5. Справочник `LC_ПартииБонусов`

Елемент створюється автоматично при нарахуванні. Код = UUID. Використовується як вимір регістру накопичення.

---

### 2.6. Службовий документ `LC_ОперацияБонусов`

Реєстратор рухів регламентного завдання (активація, згоряння).  
**Не видимий користувачу.** Створюється програмно о 00:00.

| Реквізит | Тип |
|----------|-----|
| `ВидОперации` | LC_ВидыБонусныхОпераций |
| `Комментарий` | Рядок |

Таблична часть `Партии`: `ПартияБонусов`, `Контрагент`, `Количество`.

---

### 2.7. Перерахування

| Об'єкт | Значення |
|--------|----------|
| `LC_СостоянияБонусов` | `ОжидаетАктивации`, `Доступны` |
| `LC_СтатусыБонуснойПартии` | `ОжидаетАктивации`, `Активна`, `ЧастичноСписана`, `Списана`, `Сгорела`, `Отменена` |
| `LC_ВидыБонусныхОпераций` | `Начисление`, `Списание`, `Активация`, `Сгорание`, `ОтменаНачисления`, `ОтменаСписания`, `ВозвратСписания` |
| `LC_СпособыИдентификацииКлиента` | `Телефон`, `НомерКарты`, `QRКод`, `SerialNumber` |
| `LC_СтатусыКартыLoyalCards` | `Активна`, `Неактивна` |

---

### 2.8. Інші об'єкти (без змін)

- **Константи** — параметри API (`LC_АдресСервераLoyalCards`, `LC_EmailLoyalCards`, …)
- **Справочники** — `LC_УровниЛояльности`, `LC_КартыLoyalCards`
- **Розширення** — `ЧекККМ`, `ВозвратТоваровОтПокупателя`, `Контрагенты`
- **Регламент** — `LC_АктивацияИСгораниеБонусов` (щодня 00:00)
- **Обробка** — `LC_МиграцияВБонуснуюПрограмму`

## 3. Послідовність при проведенні документів

### 3.1. ЧекККМ — проведення

```
1. LC_ИнтеграцияЧекККМ.ОбработкаПроведения()
2.   ├── Розрахунок суми списання (макс. 20% чека, FIFO)
3.   ├── LC_БонуснаяПрограммаСервер.СформироватьДвиженияСписания()
4.   │     └── Расход LC_БонусныеБаллыКлиентов (Доступны, по партіях)
5.   ├── LC_БонуснаяПрограммаСервер.СформироватьДвиженияНачисления()
6.   │     ├── Приход LC_БонусныеБаллыКлиентов (ОжидаетАктивации)
7.   │     └── Запис LC_ПартииБонусов (дати активації/згоряння)
8.   ├── LC_БонуснаяПрограммаСервер.СформироватьДвиженияОборот()
9.   └── LC_СинхронизацияLoyalCards.ЗапланироватьСинхронизацию(Контрагент)
10.      └── (після запису документа) PUT balance в API
```

### 3.2. ЧекККМ — скасування проведення

Сторно всіх рухів по регістрах документа → синхронізація балансу.

### 3.3. Повернення товарів

```
1. Знайти рухи нарахування за чеком-підставою
2. Пропорційно скасувати (ОтменаНачисления)
3. Повернути списані бонуси (ВозвратСписания) — нова партія або відновлення
4. Синхронізація balance
```

### 3.4. Регламент о 00:00

```
1. LC_ОперацияБонусов (Активация):
   - Відбір партій: ДатаАктивации <= Сегодня, не Активирована
   - Расход (ОжидаетАктивации) + Приход (Доступны)
2. LC_ОперацияБонусов (Сгорание):
   - Відбір: ДатаСгорания < Сегодня, залишок > 0
   - Расход (Доступны)
3. Для кожного зачепленого контрагента → синхронізація balance
```

## 4. Бізнес-правила

| Правило | Реалізація |
|---------|------------|
| 5% від грошової частини | `(СуммаЧека - СуммаБонусов) × ПроцентНачисления / 100` |
| Активація +14 днів | `ДатаАктивации` у `LC_ПартииБонусов`, регламент |
| Термін 4 міс. | `ДатаСгорания = ДобавитьМесяц(ДатаАктивации, 4)` |
| Макс. списання 20% | `Мин(ДоступныйБаланс, СуммаЧека × 20%)` |
| FIFO | Сортування партій за `ДатаСгорания` ASC |
| Згоряння о 00:00 | Регламент → документ → рухи |
| API sync | Тільки `balance` після рухів, ніколи навпаки |
